# JMeter 중급 - 성능 테스트 프로세스 & 결과 분석

## 1. 기능 개발 후 성능 테스트 프로세스

실무에서 새 기능을 개발하고 성능 테스트를 수행하는 표준 절차입니다.

```
1. 성능 목표 설정 (SLA 정의)
        ↓
2. 테스트 환경 구성
        ↓
3. 기준선(Baseline) 측정
        ↓
4. 부하 테스트 실행
        ↓
5. 결과 분석 & 병목 식별
        ↓
6. 최적화 적용
        ↓
7. 재측정 및 비교
```

---

## 2. Step 1: 성능 목표(SLA) 설정

테스트 전에 "얼마나 빠르면 합격인가"를 수치로 정의해야 합니다.

### 일반적인 웹 API SLA 기준

| 등급 | 응답시간 (90th Percentile) | 설명 |
|------|--------------------------|------|
| 우수 | 100ms 이하 | 사용자가 즉각적으로 느낌 |
| 양호 | 300ms 이하 | 약간의 지연 느낌 |
| 허용 | 1,000ms 이하 | 명확히 기다림 인식 |
| 불량 | 1,000ms 초과 | 사용자 이탈 시작 |

### SLA 예시 정의

```yaml
# 서비스 성능 요구사항
CRUD_조회:
  동시_사용자: 100명
  90th_Percentile: 200ms 이하
  에러율: 0.1% 이하
  TPS: 500 이상

결제_처리:
  동시_사용자: 50명
  90th_Percentile: 500ms 이하
  에러율: 0% (무조건 성공)
  TPS: 100 이상
```

## 3. Step 2: 테스트 환경 구성

### 환경 격리의 중요성

```
잘못된 환경: 개발자 PC에서 JMeter + App + DB 동시 실행
  → CPU/메모리를 나눠 써서 결과가 왜곡됨

올바른 환경: JMeter (부하 발생기) ↔ 네트워크 ↔ App 서버 ↔ DB 서버
  → 실제 운영과 유사한 환경에서 측정
```

### 로컬 테스트 시 주의사항

이 모듈은 학습 목적이므로 로컬에서 실행하지만, 결과 해석 시 아래를 감안합니다.

- JMeter가 CPU를 사용하면 App의 CPU 사용량에 영향
- 최대 동시 사용자 수를 100명 이하로 제한
- DB가 로컬이면 실제 운영 환경보다 훨씬 빠름

### HTTP 기본값 설정 (선택사항)

모든 요청에 공통으로 적용할 서버/포트를 한 곳에서 설정합니다.

```
Test Plan 우클릭
→ Add → Config Element → HTTP Request Defaults

Server Name: localhost
Port: 8090
```

이후 각 HTTP Request에서 Server/Port를 비워두면 기본값이 적용됩니다.

## 4. Step 3: 기준선(Baseline) 측정

최적화 전 현재 성능을 먼저 측정해 기록합니다.

```
기준선 없이 최적화하면 "얼마나 나아졌는지" 알 수 없습니다.
```

### 기준선 측정 시나리오

```
Thread Group 설정:
  사용자: 1명 (단일 사용자 순수 응답시간)
  Ramp-up: 1초
  Loop: 50회
```

기록해야 할 항목:
- 평균 응답시간 (Average)
- 90th Percentile
- 최대 응답시간 (Max)
- TPS

## 5. Step 4: 부하 테스트 유형별 실행

### 4-1. 부하 테스트 (Load Test)

예상되는 일반적인 트래픽에서의 성능 확인

```
Thread Group:
  사용자: 목표 동시 사용자 수 (예: 50명)
  Ramp-up: 30초
  Loop: 충분히 (예: Infinite + Duration 300초)
```

**확인 포인트**: 지속 부하 시 응답시간이 안정적인가?

### 4-2. 스트레스 테스트 (Stress Test)

한계점(Breaking Point)을 찾는 테스트

```
사용자를 단계적으로 증가:
  10명 → 50명 → 100명 → 200명 → 500명
  각 단계에서 5분씩 실행
```

**확인 포인트**: 어느 지점에서 에러율이 급증하거나 응답시간이 폭발하는가?

### 4-3. 스파이크 테스트 (Spike Test)

갑자기 트래픽이 폭증할 때의 거동 확인

```
  정상: 10명 (2분)
  스파이크: 200명 (1분, Ramp-up 5초)
  정상: 10명 (2분)
```

**확인 포인트**: 스파이크 후 정상 회복이 되는가?

### 4-4. 지속 테스트 (Soak Test)

장시간 실행 시 메모리 누수, 커넥션 고갈 확인

```
사용자: 30명
Duration: 1시간 이상
```

**확인 포인트**: 시간이 지남에 따라 응답시간이 증가하는가?

## 6. Step 5: 결과 분석 - 무엇을 봐야 하는가

### 6-1. Summary Report 읽는 법

```
Label         #Samples  Average  Min   Max    90%Line  Error%  Throughput
─────────────────────────────────────────────────────────────────────────
GET /products   5000     45ms    12ms  320ms   89ms    0.00%   87.3/sec
POST /products  2500    123ms    45ms  2100ms  198ms   0.40%   43.2/sec
```

**분석:**
- `GET /products`: Average 45ms, 90th 89ms → SLA(200ms) 충족, 정상
- `POST /products`: Max 2100ms, Error 0.40% → 비정상. 분석 필요

### 6-2. 응답시간 분포 분석

```
Average만 보면 안 되는 이유:

요청 10건의 응답시간: 50, 50, 50, 50, 50, 50, 50, 50, 50, 500ms
Average = 95ms ← 괜찮아 보임
90th Percentile = 500ms ← 실제로 10%는 500ms
Max = 500ms
```

**Average가 낮아도 90th가 높으면 일부 사용자가 느린 것입니다.**

### 6-3. Error % 분석

| Error % | 상황 | 원인 가능성 |
|---------|------|------------|
| 0% | 정상 | - |
| 0.1~1% | 주의 | 간헐적 타임아웃, 낙관적 락 충돌 |
| 1~10% | 위험 | 커넥션 풀 부족, 쿼리 느림 |
| 10% 이상 | 심각 | 서버 과부하, OOM |

### 6-4. Throughput(TPS) 분석

```
Throughput이 낮은 경우:
  - 응답시간이 길면 당연히 낮음
  - 동시 사용자 수 대비 처리 능력 부족

계산 공식:
  이론상 최대 TPS = (Thread 수) / (평균 응답시간 초 단위)
  예: 50명, 평균 100ms → 최대 TPS = 50 / 0.1 = 500 TPS
```

## 7. Step 6: 병목 지점 식별

### 병목 유형별 증상

| 증상 | 가능한 원인 | 확인 방법 |
|------|-----------|----------|
| 응답시간이 서서히 증가 | 메모리 누수, 커넥션 고갈 | 서버 메모리/커넥션 모니터링 |
| 특정 요청만 느림 | 느린 쿼리, N+1 문제 | DB 슬로우 쿼리 로그 |
| Error % 급증 | 커넥션 풀 초과, OOM | 서버 로그, Heap 덤프 |
| Max가 이상하게 높음 | GC 일시 정지 | JVM GC 로그 |
| Throughput이 특정 값에서 정체 | CPU 포화 | CPU 사용률 |

### 이 모듈에서 확인할 수 있는 병목

```
낙관적 락 vs 비관적 락:
  낙관적: Error% 높음 (충돌) / 응답시간 낮음 (빠르게 실패)
  비관적: Error% 낮음 (직렬) / 응답시간 높음 (대기)

→ "재고 감소" 같은 Write-Heavy 작업에서 비관적 락이 데이터 정합성은 보장하지만
   응답시간 증가(대기 큐)라는 트레이드오프가 있음을 수치로 확인

가상 스레드 vs 플랫폼 스레드 I/O:
  플랫폼: 200개 스레드 고정 → 201번째 요청이 대기
  가상: 제한 없이 생성 → TPS 높음, 응답시간 낮음

→ I/O 바운드 작업에서 가상 스레드가 효과적임을 수치로 확인
```

## 8. Step 7: 결과 저장 및 비교

### 결과를 CSV로 저장

```
Summary Report → 우클릭 → Save Table Data → CSV 파일 저장
```

### 두 결과 비교하기

최적화 전/후를 비교하려면:

1. 최적화 전 테스트 실행 → CSV 저장 (`before.csv`)
2. 코드 최적화 적용
3. 최적화 후 테스트 실행 → CSV 저장 (`after.csv`)
4. 두 파일의 Average, 90th, TPS 비교

## 9. 실무 성능 테스트 체크리스트

기능 개발 완료 후 성능 테스트 시 확인 항목:

```
□ SLA 기준값 사전 정의 완료
□ 테스트 환경이 운영 환경과 유사한지 확인
□ 테스트 데이터 준비 완료 (빈 DB가 아닌 충분한 데이터)
□ 기준선(Baseline) 측정 완료
□ View Results Tree 비활성화
□ 결과 초기화(Clear All) 후 실행
□ 충분한 시간 동안 실행 (Ramp-up 포함 최소 5분)
□ 서버 CPU/메모리 모니터링 병행
□ 90th Percentile 기준 SLA 달성 여부 확인
□ Error % 기준 이하 확인
□ 결과 CSV 저장 및 문서화
```

## 10. 이 모듈 성능 비교 실습

### 실습: 낙관적 락 vs 비관적 락

```
1. 02-lock.jmx 열기
2. 낙관적 락 Thread Group만 활성화 → 실행 → 결과 CSV 저장
3. Clear All
4. 비관적 락 Thread Group만 활성화 → 실행 → 결과 CSV 저장
5. 두 결과 비교
```

예상 결과 해석:

```
낙관적 락:
  Average: 낮음 (충돌 시 즉시 409 반환)
  Error%: 높음 (동시 20명이 같은 row 수정 → 충돌)
  TPS: 높음 (빠르게 처리)
  
비관적 락:
  Average: 높음 (앞 요청이 끝날 때까지 대기)
  Error%: 낮음 (직렬 처리로 충돌 없음)
  TPS: 낮음 (직렬 대기)
  
결론: 충돌 빈도가 낮으면 낙관적 락이 유리
      충돌 빈도가 높으면 비관적 락이 데이터 정합성 보장
```
