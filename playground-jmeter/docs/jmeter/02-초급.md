# JMeter 초급 - Thread Group, Sampler, Listener 완전 이해

## 1. Thread Group 상세 설정

Thread Group은 가상 사용자(Virtual User)를 정의하는 핵심 컴포넌트입니다.

### 주요 설정 항목

```
Thread Group
├── Number of Threads (users)   : 동시 가상 사용자 수
├── Ramp-up period (seconds)    : 전체 사용자가 시작되기까지 걸리는 시간
├── Loop Count                  : 각 사용자가 시나리오를 반복하는 횟수
│   └── Infinite 체크 시 무한 반복
├── Duration (seconds)          : Infinite 반복 시 전체 테스트 지속 시간
└── On Sample Error             : 에러 발생 시 동작 (Continue / Stop Thread / Stop Test)
```

### Ramp-up 계산 예시

```
Number of Threads = 50
Ramp-up period    = 10초

→ 10초 / 50명 = 0.2초마다 1명씩 추가
→ 0초에 1명, 0.2초에 2명 ... 10초에 50명 모두 활성화
```

### 언제 어떤 설정을 쓸까?

| 시나리오 | Threads | Ramp-up | Loop |
|---------|---------|---------|------|
| 빠른 연기 테스트 | 1 | 1 | 1 |
| 일반 부하 테스트 | 50 | 10 | 10 |
| 스트레스 테스트 | 200 | 30 | Infinite + Duration |
| 스파이크 테스트 | 100 | 1 | 5 |

## 2. HTTP Request Sampler 상세 설정

### 기본 설정

```
Protocol: http          ← https 사용 시 변경
Server Name: localhost  ← 또는 IP 주소
Port: 8090
Method: GET / POST / PUT / DELETE
Path: /api/products
```

### GET 요청 (Query Parameter)

```
Path: /api/products
Parameters 탭:
  Name: page, Value: 1
  Name: size, Value: 20

→ 실제 요청: GET /api/products?page=1&size=20
```

### POST 요청 (JSON Body)

```
Method: POST
Path: /api/products
Body Data 탭:
  {"name":"테스트상품","price":10000,"stock":100}

※ 반드시 Header Manager에서 Content-Type: application/json 추가 필요
```

### HTTP Header Manager 추가

POST/PUT 요청에서 JSON을 보낼 때 필수입니다.

1. HTTP Request 우클릭 → **Add → Config Element → HTTP Header Manager**
2. Add 버튼 클릭
3. Name: `Content-Type`, Value: `application/json` 입력

### PUT 요청 예시 (이 모듈의 락 경합 테스트)

```
Method: PUT
Path: /api/products/1/stock/pessimistic
Body Data: {"amount": 1}
+ HTTP Header Manager: Content-Type: application/json
```

## 3. 주요 Listener (결과 보기) 완전 해설

### 3-1. Summary Report (가장 많이 사용)

전체 성능을 한눈에 파악하는 표 형태의 리포트입니다.

```
┌──────────┬─────────┬──────────┬────────┬────────┬──────────────┬─────────┐
│ Label    │#Samples │ Average  │  Min   │  Max   │ Throughput   │ Error % │
├──────────┼─────────┼──────────┼────────┼────────┼──────────────┼─────────┤
│ GET /api │   500   │   45 ms  │ 12 ms  │ 320 ms │  87.3/sec    │  0.00%  │
└──────────┴─────────┴──────────┴────────┴────────┴──────────────┴─────────┘
```

| 컬럼 | 의미 | 판단 기준 |
|------|------|----------|
| `#Samples` | 총 요청 수 | - |
| `Average` | 평균 응답시간 (ms) | 200ms 이하 양호 |
| `Min` | 최소 응답시간 | - |
| `Max` | 최대 응답시간 | Average의 5배 이상이면 주의 |
| `Std. Dev.` | 표준편차 | 낮을수록 안정적 |
| `Error %` | HTTP 4xx/5xx 비율 | 0%이어야 정상 |
| `Throughput` | 초당 처리 건수 (TPS) | 높을수록 좋음 |
| `Received KB/sec` | 초당 수신 데이터량 | - |
| `Avg. Bytes` | 평균 응답 크기 | - |

> **Throughput vs TPS**: JMeter의 Throughput은 요청/초(requests/second)를 의미합니다. DB 트랜잭션/초(TPS)와 혼동하지 않도록 주의합니다.

### 3-2. View Results Tree (디버깅용)

개별 요청/응답 상세 내용을 확인합니다. **부하 테스트 시 비활성화 권장** (메모리 과다 사용).

```
각 요청 클릭 시:
  Request  탭: 보낸 HTTP 헤더, 바디
  Response 탭: 받은 HTTP 상태코드, 헤더, 바디
  Sampler result 탭: 응답시간, 바이트 수
```

> 에러 발생 시 실제 응답 내용을 확인하는 데 필수입니다. 정상 테스트 시에는 **우클릭 → Disable**로 꺼두세요.

### 3-3. Response Time Graph (시간대별 추이)

X축: 경과 시간, Y축: 응답시간(ms) 그래프입니다.

응답시간이 시간이 지남에 따라 올라간다면 → **메모리 누수 또는 커넥션 고갈** 의심.

### 3-4. Active Threads Over Time

시간대별 활성 스레드(사용자) 수 그래프입니다. Ramp-up이 의도대로 동작하는지 확인합니다.

### 3-5. Aggregate Report

Summary Report와 유사하지만 **백분위수(Percentile)** 정보를 추가로 제공합니다.

| 추가 컬럼 | 의미 |
|-----------|------|
| `90% Line` | 상위 90% 요청의 응답시간. 이 값이 SLA 기준 |
| `95% Line` | 상위 95% 요청의 응답시간 |
| `99% Line` | 상위 99% 요청의 응답시간 |

> **실무에서는 90th Percentile**을 응답시간 SLA 기준으로 가장 많이 사용합니다.
> "평균 50ms, 90th 200ms" = 90%의 요청이 200ms 이내에 응답

## 4. 이 모듈 테스트 파일 실행 가이드

### 사전 준비

```powershell
# 1. 앱 실행
./gradlew :playground-jmeter:bootRun

# 2. 테스트 데이터 생성 (최초 1회)
curl -X POST http://localhost:8090/api/products `
  -H "Content-Type: application/json" `
  -d '{"name":"테스트상품","price":10000,"stock":99999}'
```

### 01-crud.jmx 실행

```
File → Open → jmeter/plans/01-crud.jmx
Ctrl+Shift+E (결과 초기화)
Ctrl+R (실행)
```

Summary Report에서 확인할 포인트:
- `POST /api/products`: 50명 × 10회 = 500 요청, Error % = 0%
- `GET /api/products/1`: 50명 × 20회 = 1000 요청, Average < 100ms

### 02-lock.jmx 실행 (낙관적 vs 비관적 락 비교)

```
File → Open → jmeter/plans/02-lock.jmx
```

**예상 결과:**

| 락 전략 | Error % | Average 응답시간 |
|---------|---------|-----------------|
| 낙관적 락 | **높음** (동시 충돌 → 409) | 낮음 (빠르게 실패) |
| 비관적 락 | **낮음** (직렬 대기) | 높음 (대기 큐 형성) |

## 5. 자주 하는 실수와 해결

### 실수 1: 결과를 초기화하지 않고 재실행

이전 결과와 새 결과가 섞여 숫자가 왜곡됩니다.

**해결**: 매 실행 전 반드시 `Ctrl+Shift+E` (Clear All)

### 실수 2: View Results Tree를 활성화한 채 부하 테스트

1000건 이상 요청 시 JMeter가 메모리 부족으로 느려지거나 죽습니다.

**해결**: View Results Tree는 **Disable** 후 테스트, 디버깅 시에만 활성화

### 실수 3: 테스트 대상 앱이 꺼진 상태에서 실행

모든 요청이 "Connection refused"로 실패합니다.

**해결**: 테스트 전 `curl http://localhost:8090/actuator/health` 또는 앱 로그 확인

### 실수 4: Ramp-up = 0 으로 설정

모든 사용자가 동시에 시작 → 극단적인 스파이크 → 비현실적 결과

**해결**: 최소 `Ramp-up = Number of Threads / 2` 이상 설정
