# JMeter 심화 - 실무 패턴, CI/CD 연동, 분산 부하 테스트

## 1. 실무에서 자주 사용하는 테스트 패턴

### 1-1. 인증이 필요한 API 테스트

대부분의 실무 API는 JWT 토큰 또는 세션 쿠키가 필요합니다.

#### JWT 토큰 발급 → 재사용 패턴

```
[Thread Group]
  [HTTP Request] POST /auth/login
    Body: {"username":"test@example.com","password":"1234"}
    → JSON Extractor: $.token → accessToken 변수에 저장

  [HTTP Header Manager] (Thread Group 레벨에 추가)
    Authorization: Bearer ${accessToken}

  [HTTP Request] GET /api/products  ← accessToken 자동 포함
  [HTTP Request] POST /api/orders   ← accessToken 자동 포함
```

> Header Manager를 Thread Group 레벨에 추가하면 하위 모든 Sampler에 자동 적용됩니다.

#### 세션 쿠키 자동 관리

```
Test Plan 우클릭 → Add → Config Element → HTTP Cookie Manager

→ 추가만 해두면 JMeter가 세션 쿠키를 자동으로 저장/전송
```

### 1-2. 페이지네이션 전체 탐색 패턴

1페이지부터 마지막 페이지까지 순서대로 요청합니다.

```
[Thread Group]
  Loop Count: 10

  [Counter]  (Add → Config Element → Counter)
    Start: 0
    Increment: 1
    Maximum: 9
    Exported Variable Name: pageNum

  [HTTP Request] GET /api/products?page=${pageNum}&size=20
```

### 1-3. 특정 비율로 혼합 시나리오

실제 트래픽은 Read가 90%, Write가 10%인 경우가 많습니다.

```
[Throughput Controller] (Add → Logic Controller → Throughput Controller)
  Percent Executions: 90
    [HTTP Request] GET /api/products  ← 90% 확률로 실행

[Throughput Controller]
  Percent Executions: 10
    [HTTP Request] POST /api/products  ← 10% 확률로 실행
```

### 1-4. 조건별 분기 처리

응답 코드에 따라 다음 요청을 달리 처리합니다.

```
[If Controller] (Add → Logic Controller → If Controller)
  Condition: ${JMeterThread.last_sample_ok}
    → 마지막 요청이 성공했을 때만 실행

[If Controller]
  Condition: "${responseCode}" == "409"
    → 409 충돌 시 재시도 로직 실행
```

## 2. 실무 테스트 시나리오 설계

### 실제 서비스의 트래픽 패턴 분석

테스트 시나리오를 만들기 전에 실제 트래픽을 분석합니다.

```
분석 항목:
1. 가장 많이 호출되는 API 상위 10개 (API 로그 분석)
2. 동시 접속 피크 시간대와 사용자 수 (모니터링 대시보드)
3. 평균 세션 지속 시간 (사용자 1명이 평균 몇 분 사용)
4. API 호출 비율 (GET : POST : PUT = 7 : 2 : 1)
```

### 시나리오 설계 예시

```
전제:
  - 피크 동시 사용자: 200명
  - 평균 세션 시간: 10분
  - API 비율: 상품 조회(60%), 주문(25%), 취소(10%), 기타(5%)

JMeter 구성:
  Thread Group: 200명, Ramp-up 60초, Duration 600초(10분)

  [Throughput Controller 60%] GET /api/products
  [Throughput Controller 25%] POST /api/orders
  [Throughput Controller 10%] DELETE /api/orders/{id}
  [Throughput Controller  5%] GET /api/users/me

  각 요청 사이: Gaussian Random Timer 평균 3초 (생각 시간)
```

## 3. 모니터링과 JMeter 연계

JMeter 단독으로는 **서버 리소스(CPU, 메모리, DB 커넥션)를 모니터링할 수 없습니다.**
JMeter와 모니터링 도구를 함께 사용해야 완전한 분석이 가능합니다.

### 모니터링 스택 구성 (실무 표준)

```
[JMeter] → 부하 발생
    ↓
[애플리케이션 서버]
    ├─ Spring Boot Actuator → Prometheus 수집 → Grafana 시각화
    └─ JVM 메트릭 (Heap, GC, Threads)

[DB 서버]
    ├─ MariaDB 슬로우 쿼리 로그
    └─ DB 모니터링 (커넥션 수, Lock wait time)
```

### Spring Boot Actuator 연동

`build.gradle`에 추가:
```groovy
implementation 'org.springframework.boot:spring-boot-starter-actuator'
implementation 'io.micrometer:micrometer-registry-prometheus'
```

`application.properties`:
```properties
management.endpoints.web.exposure.include=health,metrics,prometheus
```

JMeter 실행 중 `http://localhost:8090/actuator/metrics` 를 별도 브라우저로 모니터링합니다.

## 4. CI/CD 파이프라인 연동

### 4-1. Jenkins/GitHub Actions에서 JMeter 실행

```yaml
# GitHub Actions 예시
jobs:
  performance-test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v3

      - name: Start Application
        run: ./gradlew :playground-jmeter:bootRun &
        # 앱 기동 대기
        run: sleep 30

      - name: Run JMeter Tests
        run: |
          jmeter -n \
            -t playground-jmeter/jmeter/plans/01-crud.jmx \
            -l result.jtl \
            -e -o ./jmeter-report \
            -Jhost=localhost \
            -Jport=8090

      - name: Upload Report
        uses: actions/upload-artifact@v3
        with:
          name: jmeter-report
          path: ./jmeter-report
```

### 4-2. 성능 회귀(Regression) 자동 감지

SLA를 위반하면 빌드를 실패시킵니다.

```bash
# JMeter + bash를 조합한 SLA 검증
jmeter -n -t test.jmx -l result.jtl

# jtl 파일에서 평균 응답시간 추출
AVG=$(awk -F',' 'NR>1{sum+=$2; count++} END{print sum/count}' result.jtl)

# SLA 기준 (500ms) 초과 시 빌드 실패
if (( $(echo "$AVG > 500" | bc -l) )); then
  echo "FAIL: 평균 응답시간 ${AVG}ms (기준: 500ms)"
  exit 1
fi
echo "PASS: 평균 응답시간 ${AVG}ms"
```

### 4-3. Gradle JMeter 플러그인으로 실행

이 모듈의 `build.gradle`에 이미 설정되어 있습니다.

```powershell
# 테스트 계획 실행
./gradlew :playground-jmeter:jmeter

# 결과 확인
# build/jmeter-reports/ 에 HTML 리포트 생성
```

## 5. 분산 부하 테스트 (Distributed Testing)

단일 PC로는 만들 수 없는 대규모 부하(수천 명 동시 사용자)를 여러 PC로 분산하여 생성합니다.

### 구성

```
[Controller PC] ─────────────────────────────────┐
  - JMeter GUI 실행                               │
  - 테스트 계획 작성/배포/수집                        │
                                                  │ 네트워크
[Worker PC 1] ← jmeter-server.bat 실행            │
[Worker PC 2] ← jmeter-server.bat 실행            │
[Worker PC 3] ← jmeter-server.bat 실행            │
  각 Worker가 실제 부하를 발생시킴                   ┘
```

### 설정 방법

**Worker PC에서 (각 PC마다):**
```powershell
# Worker 모드로 JMeter 실행
apache-jmeter-5.6.3\bin\jmeter-server.bat
```

**Controller PC에서:**
```
Options → jmeter.properties 편집

remote_hosts=192.168.1.101,192.168.1.102,192.168.1.103
```

**실행:**
```
Run → Remote Start All  (모든 Worker에서 동시 시작)
Run → Remote Stop All   (모든 Worker 중지)
```

### 부하 계산

```
Worker 3대, Thread Group 100명/Worker = 총 300명 동시 사용자
Controller는 부하 생성 없이 조율만 담당
```

## 6. 성능 테스트 결과 보고서 작성

테스트 결과를 팀/고객에게 보고할 때 포함해야 할 항목입니다.

### 보고서 목차

```
1. 테스트 개요
   - 테스트 목적 및 범위
   - 테스트 환경 (서버 스펙, DB, 네트워크)
   - 테스트 도구 (JMeter 버전)
   - 테스트 기간

2. 성능 목표 (SLA)
   - 목표 TPS
   - 목표 응답시간 (90th Percentile)
   - 허용 에러율

3. 테스트 시나리오
   - 테스트한 API 목록
   - 동시 사용자 수
   - 테스트 데이터 규모

4. 결과 요약
   - 항목별 측정값 표
   - SLA 달성 여부

5. 상세 분석
   - 응답시간 분포 그래프
   - TPS 추이 그래프
   - 에러 발생 패턴

6. 병목 지점
   - 식별된 병목과 원인

7. 결론 및 권고사항
```

## 7. 자주 발생하는 문제와 해결

### 문제 1: JMeter가 느리거나 OOM 발생

```
원인: GUI 모드에서 대량 요청 실행, View Results Tree 활성화

해결:
  1. GUI 대신 CLI 모드 사용
  2. View Results Tree 비활성화
  3. JMeter JVM 힙 크기 증가 (bin/jmeter.bat 편집)
     set HEAP=-Xms1g -Xmx4g
```

### 문제 2: 특정 IP에서 Connection Refused

```
원인: 방화벽, 서버가 해당 IP에서 오는 요청 차단

해결:
  1. 서버 방화벽 규칙 확인
  2. application.properties에서 허용된 IP 확인
  3. VPN 연결 확인
```

### 문제 3: 응답시간이 실제보다 높게 측정

```
원인: JMeter와 서버가 같은 PC에서 실행되어 리소스 경쟁

해결:
  1. JMeter를 별도 PC에서 실행
  2. 분산 테스트 구성
  3. CLI 모드로 JMeter 실행 (GUI 리소스 절약)
```

### 문제 4: 결과가 실행마다 다름

```
원인: GC 일시 정지, 네트워크 불안정, 서버 웜업 미완료

해결:
  1. 테스트 전 Warmup (낮은 부하로 5분 실행 후 결과 버림)
  2. 충분히 긴 시간 동안 실행 (최소 5분, 권장 15분)
  3. 여러 번 실행 후 평균 사용
```

## 8. 실무 체크리스트 (전체 요약)

```
테스트 준비
  □ 운영 환경과 유사한 테스트 환경 구성
  □ 충분한 테스트 데이터 준비 (최소 10만 건)
  □ SLA 기준값 사전 합의
  □ 모니터링 도구 준비 (Grafana 등)

테스트 실행
  □ 앱 Warmup 실행 (5분)
  □ Baseline 측정 (단일 사용자)
  □ View Results Tree 비활성화
  □ CLI 모드로 실행 (대규모 테스트)
  □ 실행 중 서버 리소스 모니터링 병행

결과 분석
  □ 90th Percentile ≤ SLA 기준
  □ Error % ≤ 허용 기준
  □ 시간대별 응답시간 추이 안정적
  □ 병목 지점 식별 및 문서화

자동화
  □ CI/CD 파이프라인에 JMeter 통합
  □ SLA 위반 시 빌드 실패 설정
  □ 결과 리포트 자동 저장 및 배포
```
